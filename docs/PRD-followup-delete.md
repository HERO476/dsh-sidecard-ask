### 0.2 一句话方案

> 卡片头部的 × 从「隐藏整个浮层」改为「**删除这条追问对话**」。删除 = 中断生成 → 丢弃增量缓冲 → 从活动卡片与持久历史按同一 `card.id` 双移除 → 立即写盘 → 关闭该卡已打开的面板 → toast 提示；**不可撤销**。「隐藏整个浮层」能力整体下线：`floatMode` 只剩 `capsule` / `full`，小圆点 launcher、设置页「隐藏」项与 4 个相关 i18n 键一并删除，不提供迁移代码（旧值走配置校验回退，见 F20）。

## 1. 对象模型

### 1.1 三层定义

| 层级 | 名称 | 定义 | 标识 | 可删除粒度 |
|---|---|---|---|---|
| T0 | 追问对话 Card | 一次划词追问产生的整张卡片（含下挂全部轮次） | `card.id`（F15） | **整组删除**（已交付：× / 历史管理器） |
| T1 | 主问答轮 | 卡片最初那条问题 + 回答（`card.question` / `card.text`） | 无独立 ID | 只能随 T0 删除 |
| T2 | 追问轮 Turn | `card.history[i] = { question, answer }` | **无 ID**（F3） | 单条删除（未交付，需先补 ID，见 M2） |

```
追问对话 Card (T0, card-1759...-3)
├── 主问答轮 (T1)                    ← 卡片首次提问 + 回答，仅随整卡删除
├── 追问轮 1 (T2, history[0])        ← 单条删除的候选（V2）
├── 追问轮 2 (T2, history[1])        ← 上下文链上依赖 history[0]
└── 当前轮   (可见区 question/text)   ← 不是 history 成员，是链的末端
```

### 1.2 两条必须记住的机制

1. **可见内容只有末端一轮**（F2/F6）：用户看到的永远是“最后一问 + 最后一答”。历史轮次只作为上下文存在，界面上没有列表、没有悬停区、没有右键菜单。
2. **history 是严格线性链**（F5）：第 k 轮的回答由 `history[0..k-1] + 当前问题` 生成。删掉中间一轮，其后所有轮次的上下文前提即失效——这决定了“单条删除”不能简单按 array splice 处理（见 §1.4 / B06）。

### 1.3 两种删除粒度的定义（本产品版）

| 粒度 | 作用对象 | 本产品下的可行形态 | 用户可见效果 | 状态 |
|---|---|---|---|---|
| **单条追问删除** | 一个 T2 追问轮 | **形态 A**：删“当前末端轮”，即**回到上一轮**——`history.pop()` 并把该条 `{question, answer}` 还原成可见内容 | 卡片内容退回上一轮，像是“撤回这次追问” | 未交付（V2 候选） |
| | | **形态 B**：在卡片内新增“轮次列表”后删除任意第 k 轮，k 之后全部级联删除 | 中间那段对话消失，后面的追问一并失效 | 未交付（V2 候选） |
| **整组追问删除** | 整个 T0 卡片 | 删除卡片 = T1 + 全部 T2 + 历史条目 + 磁盘副本 + 关闭面板 | 这张追问卡片整体消失，历史管理器里也不再出现 | **已交付（2.0.0）** |

**规则**

- D1：2.0.0 只交付“整卡删除”。形态 A / 形态 B 单列 V2，不在本次验收范围内（见 M2、M3）。
- D2：「单条删除」与「整卡删除」必须是两个入口、两套文案，禁止同一入口按数量或状态切换语义。2.0.0 只有整卡删除一个入口，因此 × 的文案与动作始终是“删除这条追问对话”。
- D3：不做“清空追问但保留主问答”的第三模式（v1 的 M3）。理由：本产品追问链是上下文链，清空 history 与“删除所有 T2”等价，而用户真正想要的“清上下文、留当前问答”= 形态 A 的逆向，没有独立价值，徒增入口。

### 1.4 层级硬约束（可测试）

| 编号 | 约束 | 断言方式 |
|---|---|---|
| H1 | 任意删除操作的定位键是 `card.id`，禁止用数组下标定位卡片 | 代码审查：不存在 `cards[i]` 形式的删除 |
| H2 | 删除 T0 后，同页面内该 `card.id` 永不复用 | 删除后新建卡片，断言 ID 不等于被删 ID（F15 自增段保证） |
| H3 | 删除只减少 `history` 长度，不产生空洞、不重排 | `history.length` 单调不增；元素对象引用不变 |
| H4 | 删除 T2 形态 B 时，`k..n` 一并删除，不留“孤儿轮”（未交付，V2 候选） | 断言 `history.length === k` |
| H5 | 删除是同步完成的，不存在“删除中”可交互窗口；确认层打开期间该卡不响应 R/C/Esc | `client.js:4141` 早退；断言按键无效 |
| H6 | 删除卡片即删除其 `versions`（F16），两者不分离 | 删除后 localStorage 中该 ID 无残留（整卡条目整体丢弃） |
| H7 | 删除不改变其它卡片的 `id`、顺序、`createdAt` | 删除前后其余卡片快照 diff 为空 |

> **本次已消除的语义错位**：2.0.0 之前，× 是「隐藏整个浮层」——只把浮层收进一个带计数的小圆点，历史条目一条不动（这正是 F10 注释所说的“关闭只摘离活动面，持久历史保留”）。用户把它当作“删除这张追问”，是现有语义与心智模型错位。2.0.0 把这枚 × 直接改成删除，并**不再提供**任何“隐藏浮层”的入口。
>
> **承载面差异（必须如实写进验收）**：× 只出现在**浮层**上。被宿主 tab 承载的同一张卡（`better-sidebar` / `native-rightbar` 独立标签页）不传 `onFloatMode` / `onDelete`，因此**既没有 ⇥ 也没有 ×**（F8）；它的关闭语义是宿主标签关闭 + 卡片底部「关闭」，二者都**不删历史**。删除这类卡片目前只能进设置页历史管理器。

|---|---|---|---|---|---|---|
| E1 | 卡片头部 × | 浮层卡片（`full` 形态） | 单击 | P0 | **已交付（2.0.0）** | **主入口**，语义 = “删除这条追问对话”（D0） |

### 2.3 决策 D0：× 的语义改造（**已定稿，2026-10-18 用户拍板**）

**结论**

- **D0 = × 直接承载「删除这条追问对话」**：单击 × 即进入删除流程（空卡直接删，其余弹插件内确认层），删除同时作用于活动卡片与持久历史。
- **「隐藏整个浮层」能力整体删除**：不是挪位置、不是收进菜单、不留替代入口。具体落地为——`floatMode` 枚举去掉 `off`（只剩 `capsule` / `full`）、小圆点 launcher 的渲染分支与样式删除、设置页 floatMode 下拉只剩两项、`setFloatModeOff` / `floatHide` / `floatRestore` / `floatCount` 四个 i18n 键删除。
- 「收起为胶囊」（⇥）**保留**：它仍是“别挡着对话”的唯一入口，与“隐藏”不是同一需求——收起后浮层仍以一行胶囊可见、可一键展开；隐藏是“连胶囊也不要”，属于低频全局操作。

**决策依据（保留原比选分析）**

| 方案 | 做法 | 优点 | 代价 | 取舍 |
|---|---|---|---|---|
| **D0-A（采用）** | × 改为“删除本条追问对话”；浮层整体隐藏能力不再提供 | 与用户心智一致，删卡最顺手；语义唯一，不存在“同一个 × 两种命运” | 失去“连胶囊也不要”的全局隐藏能力 | **采用**：隐藏属低频操作，且与 ⇥ 收起高度近似，保留两套入口的解释成本高于收益 |
| D0-B | × 保持“隐藏浮层”，新增 ⋯ 菜单收纳「关闭」「删除」 | 改动最小、零学习成本 | 用户仍会把 × 当删除；删除入口多一次点击 | 不采用：错位正是本需求要修的问题 |
| D0-C | × 改为“关闭（保留历史）”，删除只放底部 E2 与历史管理器 | 语义最保守 | 与用户明确诉求（“删除指的是这个”）不符 | 不采用：直接违背拍板结论 |

**附带约束**

- 不做配置迁移代码：旧配置里的 `'off'` 由宿主配置校验判为非法值 → 忽略并回退默认 `capsule`，同时在 `problems` 里给出提示（F20）。
- 不新增“隐藏浮层”的替代入口：⇥ 菜单项、浮层边缘把手、胶囊长按**全部不实现**（该能力已整体下线），见 §8 Q1。
- 文档与文案中不得再出现“隐藏浮层”作为可执行能力（该能力已于 2.0.0 下线）；历史版本说明（CHANGELOG 1.5.0）保持原样，属历史记录。

## 3. 交互流程

### 3.1 整卡删除（E1，已交付路径）

| 步 | 界面 | 系统动作 | 代码位置 |
|---|---|---|---|
| S1 | 用户点 × | `requestDelete()`：`busy`（pending/streaming）**或**卡片非空 → 打开确认层；空卡 → 直接跳 S4 | `client.js:4176–4182` |
| S2 | 确认层出现 | 标题 `cardDeleteTitle`「删除这条追问对话？」；正文 `cardDeleteBody`「会同时从浮层和追问历史里移除，且不可撤销。」；`history.length > 0` 时追加一行 `cardDeleteRounds`「含 {n} 轮追问」；按钮 `[取消] [删除]` | `client.js:4360–4372`、`4040–4077` |
| S3 | 点「取消」/ `Esc` / 点遮罩 | 只关闭确认层，不发任何请求、不动数据 | `client.js:4042–4052`、`4367` |
| S4 | 点「删除」 | 先 `setDeleteOpen(false)` 关确认层，再 `actions.deleteCard(card)` | `client.js:4368–4371`、`4587` |
| S5 | （无中间态界面） | 若有 controller：`controller.abort()` → `void postJson('cancel', { id }).catch(() => {})` → `controllers` / `pendingDeltas` / `pendingReasonings` 全部按 id 删除 | `client.js:5716–5723` |
| S6 | 卡片消失 + toast | `nextHistory = history.filter(id).slice(0, historyCap())`；`historyCap() > 0` 时 `writePersisted(nextHistory)`；`store.set({ history, cards })` 双删；关面板；`toast(t('cardDeleted'))` | `client.js:5727–5748` |
| S7 | 浮层重排 | 剩余卡片按原顺序塌缩补位；若删掉的是最后一张，`total === 0` → 浮层**整体不渲染**（无空态；小圆点 launcher 已于 2.0.0 移除） | `client.js:4537`、`4570–4588` |

**说明**：S5 的 `cancel` 是 fire-and-forget（不 `await`），失败被 `.catch(() => {})` 吞掉，不阻断删除；删除全部动作在同一同步块内完成，没有“正在删除”的中间界面（该视觉反馈属未交付，见 §3.5）。

### 3.2 单条删除（形态 A：回到上一轮，E4）——未交付（V2 候选）

| 步 | 界面 | 系统动作 |
|---|---|---|
| S8 | 用户在卡片追问区上方点「← 回到上一轮」 | 无确认 |
| S9 | 卡片内容切换为上一轮问答，追问区收起 | `history.pop()` → 写回 `question`/`text`/`reasoning` → 清 `error`/`streaming` |
| S10 | toast「已回到上一轮 · 撤销」5s | 快照 = `{ history, question, text, reasoning, status }` |

**规则**

- D7：形态 A 必须**完整还原**上一轮的 answer（`history` 里存了 `answer`，F3），不能只改问题、答案重新生成——重新生成既慢又可能不一致。
- D8：形态 A 不改变 `versions`（F16）；版本是“同一轮的多次回答”，与“回到上一轮”不同概念。
- D9：`history` 为空时 E4 不显示，不做禁用态（避免解释成本）。

### 3.3 单条删除（形态 B：任意轮）——未交付（V2 候选）

- 必须先有“轮次列表”UI（当前不存在，F6），列出 `history[0..n-1]`；每行 = 问题 + 回答摘要 + `⋯`。
- 删除第 k 轮 → 级联删除 `k..n-1`，确认层必须写明「将同时删除其后的 M 轮追问」。
- 删除后当前可见轮若被级联，卡片回退到 `history[k-1]`；若 k=0，回到 T1 主问答轮。
- 埋点与验收不在本次范围（D1）。

### 3.4 二次确认规格（**与已交付代码逐条对齐**）

| 项 | 有内容（以下任一成立：`history.length > 0`、正文非空、思考过程非空、`pending`/`streaming`） | 空卡（`history.length === 0` 且正文与思考过程皆空 且 不在作答中） |

| 正文 | 「会同时从浮层和追问历史里移除，且不可撤销。」（`cardDeleteBody`） | — |
| 轮次数 | **仅当 `history.length > 0`** 时追加一行「含 {n} 轮追问」（`cardDeleteRounds`，`{n}` 插值） | — |

**规则**

- D10：确认层禁止默认聚焦危险按钮（防连按 Enter）——已交付，焦点固定在「取消」。
- D11：确认文案禁止写「确定吗？」；必须写明对象（**这条追问对话**）与不可撤销；轮次数**只在有轮次时**出现，不写“0 轮”。
- D12：空卡判定比“只看 `text`/`history`”更严：`history.length === 0 && text.trim() === '' && reasoning.trim() === '' && !busy`。多出的 `reasoning` 与 `busy` 两个条件是为了不误删“已产出思考内容但正文还没开始写”或“请求已发出、首字未到”的卡片——这类卡删掉同样会丢东西，必须走确认。

## 4. 边界场景

> 每项：现象 → 根因 → 规则（编号 CB\*，对应 §6.4 用例）。标 `未交付` 的条目为候选设计，不代表 2.0.0 行为。

### B01 删除正在流式输出的卡片

- 现象：卡片删了，回答仍在服务端继续生成，随后可能推回增量。
- 根因：`abort()` 只断本地连接；必须同时通知宿主停止子代理。
- 规则：
  - **CB1** 删除 `streaming` 卡片，顺序固定：`controller.abort()` → `POST /sidecard-ask/api/cancel {id}` → 清 `pendingDeltas`/`pendingReasonings` → 删卡片（已交付，`client.js:5716–5723`）。
  - **CB2** `cancel` 失败不阻断删除（`.catch(() => {})`，`client.js:5719`），也不弹提示（无失败计数上报，属 N/A：无遥测）。
  - **CB3** 删除后若仍收到该 `id` 的 `delta`/`done` 事件，不得重建卡片：`patchCard` / `appendCardText` 按 id 查找，卡片已不在则 no-op（`client.js:1399–1401`、`1406–1411`）。
  - **CB4** 2.0.0 **没有**「正在停止生成…」→「正在删除…」的分段文案：删除是一次同步调用，界面从确认层直接进入“卡片已消失 + toast”。该分段文案属未交付（§3.5）。

### B02 pending / 未开始

- **CB5** `status === 'pending'`：删除时同样走 abort + cancel（请求可能已发出），且**必弹确认**——`busy` 会短路空卡直删路径（`client.js:4172`、`4177`）。
- **CB6** 空卡（`history.length === 0` 且 `text` 与 `reasoning` 皆空且不在作答中）删除不弹确认（D12）；删除后同样弹一次 toast「已删除这条追问对话」。

### B03 迟到增量与事件竞态

- **CB7** 2.0.0 **没有**显式的 `deletedCardIds: Set` 墓碑集合；等价保证由“按 id 更新、找不到即 no-op”提供（`client.js:1399–1401`、`1406–1411`）。迟到事件不会重建卡片（不是“隐藏”，是找不到目标）。
- **CB8** 删除时同步 `controllers.delete(id)`、`pendingDeltas.delete(id)`、`pendingReasonings.delete(id)`（`client.js:5721–5723`；`close` 走同一套，`client.js:6101–6105`）。
- **CB9** 50ms 合批 tick 里不得对被删卡片执行 flush：缓冲已在删除时按 id 清除，flush 按剩余条目遍历（`client.js:6153–6157`）。

### B04 活动卡片与历史条目双写

- 现象：卡片删了，刷新后又出现在历史管理器里。
- 根因：`state.cards` 与 `state.history` 是两份，写盘由 `syncPersisted` 从 `cards` 推导（`client.js:5508` 起）。
- 规则：
  - **CB10** 删除必须同时改两份：`cards` 过滤 + `history` 过滤 + `writePersisted(下一个 history)`（已交付，`client.js:5736–5746`），与 `deleteHistoryCard`（`client.js:5688–5698`）保持同一写法。
  - **CB11** 不允许只改 `cards` 后依赖下一次 `syncPersisted` 兜底——该函数按“终态且有正文”重建，pending/error 卡片本来就进不了历史，语义会漂移。
  - **CB12** 删除后立即断言 `localStorage` 中该 `card.id` 不存在（含 v3/v2/v1 三代键的迁移路径，F14）。

### B05 上下文窗口重算

- 现象：删掉一张卡后，别的卡的回答“记住了”被删内容。
- 根因：上下文只取本卡 `history`（F5），卡片之间不共享上下文。
- 规则：
  - **CB13** 卡片之间无上下文共享：删除 A 卡不影响 B 卡的下一次请求；断言 B 请求体不含 A 的任何文本。
  - **CB14** 若将来实现卡内删除（形态 A/B），下一次请求的 `history` 必须即时反映新长度，无需刷新（未交付，V2 候选）。
  - **CB15** `history` 变短不得“补足”到原长度；宁可用更少上下文。
  - **CB16** 形态 A 之后 `history` 长度减 1，`prompt` 里不得再出现被退回那轮的问题文本（未交付，V2 候选）。

### B06 轮次级联（形态 B）——未交付（V2 候选）

- **CB17** 删除第 k 轮 → `history = history.slice(0, k)`，其后全部失效。
- **CB18** 级联范围在确认层明示「同时删除其后 M 轮」。
- **CB19** 不允许留下 `history[k-1]` 之后仍被“当前轮”引用却已删除的中间态。

### B07 版本回看

- **CB20** 回看旧版本（`viewingVersion !== null`）时删除：删除整卡，回看态直接丢弃，不需要先“回到最新”（已交付：确认层与删除逻辑不依赖回看态）。
- **CB21** 删除卡片必须连带删除 `versions`（H6）：整卡条目从 `cards` / `history` 中移除，磁盘只重写剩余条目。

### B08 持久化三键与迁移

- **CB22** 单卡删除只改写当前版本键（v3），**不得**清 v2/v1——否则会破坏非破坏式迁移的前提（`client.js:5451–5453`、`5475–5496`）。
- **CB23** 只有「清空全部」（F12）允许删三代键（`client.js:5763–5765`）。
- **CB24** 写盘失败（配额/隐私模式）不阻断删除：`writePersisted` 内部 try/catch，只 `console.warn`，**不追加 toast 提示**（当前实现，`client.js:5498–5505`）。用户可见的“本地记录未能保存”提示属未交付。

### B09 多标签页 / 多窗口

- 现象：标签页 A 删除，标签页 B 仍显示。
- 根因：无 `storage` 监听，无服务端推送（F18）。
- 规则：
  - **CB25** 明确不支持实时同步；B 标签页在下一次刷新后与磁盘一致。
  - **CB26** 若后续要支持，加 `window.addEventListener('storage')` 监听 v3 键并重建 store，属独立需求。
  - **CB27** 「多端同步冲突」在本产品**不适用**，乐观锁 / 409 / revision / 孤儿上挂这一整套规则不得照搬。

### B10 面板形态差异

- **CB28** 浮层（flow）内删除：无塌缩动画，剩余卡片直接重排（`client.js:4537`、`4570–4588`；180ms 塌缩属未交付）。
- **CB29** `better-sidebar`/`native-rightbar` 内嵌卡片：删除后必须调用对应 `surfaces.*.close(card)`，否则留一个空面板（已交付，`client.js:5727–5735`）。
- **CB30** 面板头部关闭按钮与宿主标签关闭（宿主提供）语义是“关面板”，不得改成删除；删除入口固定在浮层卡片头部（E1）。**注意**：宿主 tab 里渲染的同一张卡没有 ×（F8），这类卡片删除只能走设置页历史管理器。

### B11 主对话载体（`carrier === 'main'`）

- **CB31** `carrier === 'main'` 的卡片是“已改发到主对话”的记录，删除它只清理本地记录，不影响主对话里已经发出的内容。**当前确认层正文没有单独写这一句**（`cardDeleteBody` 只写“从浮层与追问历史移除、不可撤销”）；如需更强的告知，属文案增强（未交付）。
- **CB32** 该状态下不提供 E4（没有 side 语义的追问链）；E4 本身也未交付。

### B12 历史容量与极值

- **CB33** `historyCap() === 0`（停用持久化，F13）时，删除只作用于内存：`deleteCard` 在 `historyCap() > 0` 为假时**不写盘**（`client.js:5739–5742`），保留原键不动。
- **CB34** 历史条目被容量挤掉（cap 上限 50）后，再删该卡片只影响内存，不得报错。

### B13 引用与导出

- **CB35** 导出（Markdown）不含已删卡片；已打开的导出预览不追溯更新。
- **CB36** 「定位原文」（`locate`）对被删卡片不可达：入口随卡片消失，不做“原文已删除”占位（本产品没有引用块）。

### B14 键盘与无障碍

- **CB37** 卡片键盘 `Delete` 触发删除：**未交付（V2 候选）**。现有关键盘契约只有 R 重试 / C 复制 / Esc 释放焦点（`client.js:4137–4160`、`4151–4159`）。
- **CB38** 确认层 `role="dialog"` + `aria-modal` + `Esc` 关闭 + 取消键 `autoFocus`：**已交付**（`client.js:4054–4071`）；**焦点陷阱与“关闭后焦点归还触发按钮”未交付**。
- **CB39** 删除完成**无屏幕阅读器播报**（未交付）：现状只有可见 toast「已删除这条追问对话」。不存在“可撤销”播报。

### B15 存储异常

- **CB40** `localStorage` 不可用（隐私模式）：删除照常执行，仅内存生效（与 `writePersisted` 的 try/catch 语义一致，`client.js:5498–5505`）。

## 5. 数据一致性规则

### 5.1 数据结构（现状，不新增字段的前提下）

| 字段 | 位置 | 删除时的处理 |
|---|---|---|
| `card.id` | 卡片 + 历史条目 | 定位键，删除后不复用 |
| `card.history[]` | 卡片 + 历史条目（`slice(-12)`，F4） | 整卡删除：整体丢弃；形态 A（未交付）：`pop()` |
| `card.question` / `text` / `reasoning` | 卡片 + 历史条目 | 随整卡丢弃；形态 A（未交付）：用 `history` 末尾条目回填 |
| `card.status` / `error` / `streaming` | 仅内存 | 删除即丢弃 |
| `card.versions[]` | 卡片 + 历史条目 | 随卡片删除（H6） |
| `state.cards` / `state.history` | 内存 | 双写（CB10） |
| `localStorage[v3]` | 磁盘 | 重写整个数组（`writePersisted`，`client.js:5500`） |

### 5.2 删除事务（顺序固定，与 `client.js:5713–5749` 一致）

1. 校验 `card.id`：不是非空字符串 → 返回 `false`，无任何副作用。
2. 若有 controller：`controller.abort()` → `POST /sidecard-ask/api/cancel {id}`（不等待、失败吞掉）。
3. 清 `controllers` / `pendingDeltas` / `pendingReasonings`。
4. 关闭该卡已打开的面板：`surfaces.better.close(card)` / `surfaces.native.close(card)`（各自 try/catch）。
5. 计算 `nextHistory = history.filter(id).slice(0, historyCap())`；`historyCap() > 0` 时 `writePersisted(nextHistory)`。
6. `store.set({ history: nextHistory, cards: cards.filter(id) })`。
7. `toast(t('cardDeleted'))`，返回 `true`。

**规则**

- TX1：第 5、6 步必须同一同步块内完成，中间不 `await`（当前实现满足：`client.js:5736–5746` 无 `await`），避免出现“磁盘已删、内存未删”的中间态被下一次 `syncPersisted` 覆盖回写。
- TX2：第 5 步失败（配额）→ 仍执行第 6 步；但当前只 `console.warn`，**不弹“本地记录未能保存”**（CB24，属未交付增强）。
- TX3：幂等——同一 id 重复删除不会复活卡片（两份存储都按 id 过滤），也不会重复写盘出第二份数据；`id` 非非空字符串时返回 `false`。**注意**：对格式合法但已不存在的 id 调用仍会弹一次 toast（无副作用），这是已知粗糙点，如需“静默 no-op”属后续优化。
- TX4：（未交付，V2 候选）撤销 = 按快照回填 `cards` 与 `history` 并 `writePersisted`，不重新请求。
- TX5：删除后 `state.history.length ≤ historyCap()` 恒成立（第 5 步的 `slice` 与 F13 截断一致）。

### 5.3 服务端与跨端：明确标注不适用

| v1 条款 | 本产品结论 |
|---|---|
| 服务端软删/硬删、30 天审计 | **N/A**：插件侧没有会话存储接口（路由仅 `state/ask/cancel/config/reset/diagnose/feedback`，`index.js:2283`；磁盘只写 `config.json`，`index.js:1914`、`index.js:1934`），卡片内容只在浏览器 `localStorage` |
| 多端同步、409 CONTEXT_GONE、revision 乐观锁 | **N/A**：没有对端 |
| 离线队列、重连重放 | **N/A**：无写服务端动作 |
| 摘要 stale 重建 | **N/A**：无摘要机制 |
| Token 预算重算 | **降级**：上下文就是 `history.slice(-6)`（F5），删除后自动变短，无需单独重算 |

> 这些条款若将来产品引入服务端会话库，应作为**新需求**重新评估，而不是在本文档里假装已实现。

### 5.4 一致性表（本产品的“多方”只剩内存两份 + 磁盘一份）

| 场景 | 内存 `cards` | 内存 `history` | 磁盘 `v3` | 允许的中间态 |
|---|---|---|---|---|
| 删除成功（`historyCap() > 0`） | 已移除 | 已移除 | 已重写 | 无（同步块内完成） |
| 删除成功（`historyCap() === 0`） | 已移除 | 已移除 | **不动**（保留原键） | 允许：本就不持久化（CB33） |
| 删除后撤销 | — | — | — | **未交付（V2 候选）**，当前不存在该状态 |
| 写盘失败 | 已移除 | 已移除 | 仍含该项 | **允许**，刷新后可能“复活”；当前无用户提示（CB24） |
| 刷新页面 | 从磁盘重建 | 从磁盘重建 | — | 无 |
| 另一标签页 | 不感知 | 不感知 | 已更新 | **允许**，刷新后一致 |

### 6.8 非目标

- 不做服务端会话删除、跨端同步、离线队列（§5.3；N/A）。
- 不做回收站/历史压缩摘要重建。
- 不做“删除后自动重生成”。
- 不改宿主主对话的消息（`carrier='main'` 只清本地记录）。
- **不恢复「隐藏整个浮层」能力**：不新增 launcher、不给 `floatMode` 加回 `off`、不在 ⇥ 菜单或浮层把手等处补替代入口（D0 定稿，§8 Q1）。
- 不做形态 B（任意轮删除）的 UI，除非 V2 立项（D1）。
- 不做撤销（5 秒窗口/快照）、删除中视觉反馈、历史管理器补确认、键盘 Delete —— 均登记为 V2 候选（§0.4）。

**接口形态**：本仓库是 RPC 风格 `POST /sidecard-ask/api/{method}`（`index.js:50`、路由表 `index.js:2343`）。删除**不需要新接口**——历史在浏览器本地，唯一需要调用的是既有 `cancel` 路由。因此 v1 里写的 `POST /delete-turn`、`DELETE /sessions/...` 全部作废，不要照抄。
